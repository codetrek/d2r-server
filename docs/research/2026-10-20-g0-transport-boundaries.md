# G0：内部传输、连接与缓冲区边界

日期：2026-10-20。状态：完成限定范围的静态分析及独立入口编解码；**G0–G5 均未通过**。

本报告补充[协议与运行时证据](../design/2026-10-20-protocol-research.md)及[四人私服设计](../design/2026-10-20-d2r-server-design.md)。该静态子任务的研究对象是自有 v1.0.18 游戏产物；当时没有运行游戏、连接官方服务或操作真实角色。后续独立的 [Mac 单机运行基线](2026-10-20-mac-runtime-fixture.md)已经进入世界并保存退出，后续[原生观察实验](2026-10-20-native-transport-probe.md)还完成本地系统/玩法逐通道字节对照；这些独立执行都不能扩大为双进程或多人验证。以下偏移均相对于该构建的 `main` 映像，名称均为分析标签，不能跨版本使用。所有偏移均依赖已初始化的原程序上下文，不是可独立调用的 Linux API。

## 结论与当前交付

已找到客户端发送、服务端双队列、接收调用、默认下行方法及部分连接生命周期的实际实现。此前接收函数“前移四字节却保留长度”的疑问已经解决：**调用方传入的长度本来就不含连接编号**。

默认下行实现只交付本地连接 `0`。四人远程联机需要新的逐连接路由与客户端桥接。下行方法还会进入字节流解析器；一次发送调用的字节范围不能直接视为一个客户端事件或一个网络帧。

本仓库新增 `internal/guestingress`，准确实现两种内部入口表示的独立编解码及字节归属测试。它尚未向游戏队列插入内容、调用游戏函数、处理套接字或建立网络服务。控制进程仍报告引擎不可用，`/readyz` 返回 503，`multiplayer_available` 为 `false`。

## C2S：载荷、队列项和接收调用

```mermaid
flowchart LR
  Payload[原程序载荷字节] --> Send[客户端发送端口]
  Send --> Copy[同步复制并选择内部队列]
  Copy --> Sys[系统队列]
  Copy --> Game[玩法队列]
  Sys --> Pump[原程序线程收包泵]
  Game --> Pump
  Pump --> Bind[连接、房间与玩家查找]
  Bind --> Dispatch[玩法或系统处理]
```

| 边界 | 已观察到的表示或行为 |
|---|---|
| 客户端提交 | `0x2ceab0` 使用内嵌对象 `0x2d9f438` 的虚方法 `+0x30`，传入 `{begin,end}` 载荷范围。连接号没有放在这个范围里。此发送入口另有重复抑制、进度发送和局部 `<512` 长度条件。 |
| 默认客户端方法 | 虚表 `0x20afbc0` 的 `+0x30` 为 `0x840354`。本地模式调用 `0x83e80c`，带上服务端对象、连接号 `0` 及载荷范围；其他模式分支不构成本项目已经接入的网络后端。 |
| 本地入队 | `0x83e80c` 根据首字节选择队列：`<0x67` 为玩法，其余为系统。它把长度、连接号和载荷复制进可扩展的自有缓冲区。 |
| 一条队列项 | 小端 `[u16 载荷长度][u32 连接号][载荷]`，总长为载荷长度加 6。系统队列位于服务端对象 `+0x10020`，玩法队列位于 `+8`。 |
| 队列弹出 | 服务端虚方法 `+0x50` → `0x84d6cc` 读取系统项；`+0x58` → `0x84d778` 读取玩法项。返回范围去掉 `u16`，保留连接号；游标增加载荷长度加 6。范围借用原队列存储。 |
| 接收调用 | `0x5d3960` 先抽干系统队列，再抽干玩法队列；立即复制返回范围，并传入 `[u32 连接号][载荷]` 与**单独的载荷长度**。可访问缓冲区范围必须是长度加 4。 |
| 玩法接收 | `0x632510` 查找完整连接号、房间与玩家，前移指针四字节后，把原本已经排除前缀的长度传给 `0x6e5b40`。 |

队列弹出范围会受后续扩容、重置和存储生命周期影响。新适配器必须在借用范围失效前复制，且由原程序线程拥有引擎调用。静态代码没有证明队列可被网络线程并发访问。

公开源码也独立支持载荷长度约定：[接收与改写路径](https://github.com/jhaizhou-ops/d2r-mobile/blob/120fe55c02a5633476998a44f8c3c3c809fa48b0/dm/host/diag.c#L1316)保留四字节前缀，改写后的载荷为 25 字节时仍传入长度 25；[系统回放](https://github.com/jhaizhou-ops/d2r-mobile/blob/120fe55c02a5633476998a44f8c3c3c809fa48b0/dm/host/diag.c#L1378)同样单独构造前缀。

### 已实现的内部编解码

`Message` 包含 `ClientID uint32` 与不透明的 `Payload []byte`。连接绑定、消息分类和授权由调用方负责。

| API | 精确契约 |
|---|---|
| `EncodeQueueEntry` | 生成一条自有队列项；载荷超过 `MaxQueuePayload = 65535` 时失败。 |
| `DecodeQueueEntry` | 只接受一条长度完全匹配的队列项；拒绝截断、长度不符和尾随字节，返回独立的载荷副本。 |
| `EncodeReceiverBuffer` | 生成自有的连接号加载荷缓冲区，同时返回排除前缀的 `uint32` 载荷长度；检查长度及平台整数溢出。 |
| `DecodeReceiverBuffer` | 要求输入恰好等于四字节前缀加声明长度，返回独立载荷副本。 |

编解码允许连接号 `0` 和空载荷，因为这一层只描述字节表示。这不表示任何原程序消息或接收入口接受空载荷。`65535` 只是队列项 `u16` 字段的表示上限；接收表示使用独立的 `uint32` 长度，另受平台分配范围限制。两者都不是已验证的线上帧上限、原程序栈缓冲区上限或可安全调用引擎的通用长度限制。

这四个 API 不实现整个环形或动态队列，不选择系统/玩法通道，不生成 WSS 帧，也不验证操作码、角色数据、身份、调用线程或游戏生命周期。

## 连接、入场与待处理指令

构造器 `0x850610` 把内嵌服务端对象 `0x2d7f3d8` 绑定到虚表 `0x20afb40`，把内嵌客户端对象 `0x2d9f438` 绑定到 `0x20afbc0`。这是 Ghidra 正确入口和 LLVM 的结论；Hopper 本轮没有识别构造器，不能把该查询失败计为独立佐证。这些是静态默认构造结果；运行时模式切换是否替换虚表、其他实现是否具有不同路由仍待验证。

系统分发入口 `0x6310b0` 在此补丁映像中先经过包装层，分析主体 `0x6310b4` 使用 `0x1daf73c` 的十项分发表。`+4` 仅用于反编译观察，不是安全的 ABI 调用入口；未来桥接必须保留 `0x6310b0` 的 TLS/SVC 包装及原程序线程上下文。已观察到的路径如下：

| 消息 | 已观察到的生命周期作用 |
|---|---|
| `0x67` | 401 字节载荷路径调用游戏创建函数 `0x5d0bd0`。上游文档笼统称其为“加入”，需与后续准入区分。 |
| `0x68` | 85 字节载荷路径执行房间容量及其他准入判断，调用连接分配，将连接置为状态 1，并发出初始化通知。 |
| `0x6c` | 在已分配连接的加载状态下，将角色数据分段交给逐连接的缓冲区处理。完整角色格式及加载到活跃状态的链路仍未知。 |
| `0x6d` / `0x6f` | 分别为 13 / 5 字节的心跳与进度路径，维护逐连接状态。 |
| `0x69` / `0x70` | 到达不同的离开/移除路径；完整保存、断线触发及恢复行为仍待验证。 |
| `0x6a` / `0x6b` / `0x6e` | 此主体中进入默认返回分支。 |

连接分配 `0x5d9810` 保存完整连接号与房间指针，再加入房间客户端链和全局按低八位分桶的连接链。后续查找会比较完整编号。这是引擎内部归属，不能作为远程认证；网关仍需把已认证会话绑定到服务器分配的连接号。

玩法接收的第四个参数是**带标签的回调持有者地址**。泵传入值为 1 的持有者，表示没有实际回调对象；直接传空指针不满足相同契约。分发返回特定的待处理结果时，接收方可能调用持有者内的虚方法，或保留原连接号加载荷以便后续重试。

限定分析确认待处理副本有独立长度、记录逻辑帧和初始为 25 的重试预算；后续回调仅在游戏逻辑帧改变后重试，并更新预算和记录帧。泵在双队列处理后推进待处理集合。完整持有者释放、容器移除及所有失败清理尚未查明。新的桥接必须保留这条路径，不能直接调用玩法分发器来替代接收生命周期。

## S2C：默认本地路由与字节流

[属性通知源码](https://github.com/jhaizhou-ops/d2r-mobile/blob/120fe55c02a5633476998a44f8c3c3c809fa48b0/dm/host/dm_elysium.c#L325)传入服务端对象、单独的接收方编号及 `{begin,end}`；它证明调用边界具有接收方参数。本轮恢复的默认虚方法 `+0x28` → `0x84cdd8` 则只在接收方为 `0`、本地模式及相关状态满足时交付。因此，源码中的逐接收方参数不能被解释为已有通用远程投递能力。

该方法将载荷范围交给 `0x84178c`。限定反编译显示它有定长/变长消息分支、部分字节缓冲、逐完整消息回调及重入时的复制队列。一次发送范围、一次解析完成的消息、一次客户端事件和一次网络帧是不同的边界；完整 S2C 类型集合、压缩与所有变长规则仍未恢复。

调用方可能提供栈上的载荷和范围结构。替换方法必须在返回前取得自有字节副本，再交给异步网络发送；不得跨进程传指针，或让网络任务持有借用的栈地址。接收侧需要保留字节顺序和经过验证的流边界，不能依据一次发送调用擅自拆成客户端事件。

## 验证结果与剩余门槛

本静态边界变更时的 `make check` 通过格式、静态检查、竞态与覆盖率要求；当时核心包总覆盖率 88.4%，其中 `guestingress` 为 90.6%、`control` 为 98.3%、`guestlayout` 为 86.0%。后续双模块与 Mac 工具变更的当前检查记录见[开发说明](../development.md)，不回写历史覆盖率。独立代码审查未留下 critical/major。测试覆盖精确字节表示、截断与尾随数据、边界长度、整数范围和多次编解码之间的独立字节归属，使用的都是合成数据。这些结果不证明游戏入口可调用，也不替代本分支的 Docker 或远程 CI 记录。

G0 仍需完整的生命周期与所有权约定，以及自有客户端双进程往返；G1 仍需 Linux 原程序初始化、独立时钟、资源、存档和无画面生命周期。后续资源准备、真实生成器和固定 Mac 候选执行已分别取得记录，详见 [Mac 运行报告](2026-10-20-mac-runtime-fixture.md)。这形成单机执行基线，后续原生观察已取得本地逐通道输入/出队对照，但未完成双进程往返；Linux 无界面生命周期依然未通过。

必须继续验证：加载到活跃及离开清理的完整链路、重连、逐连接下行路由、S2C 边界和压缩、待处理集合释放、各操作码及各层缓冲区限制、同房间四人归属和一致检查点。G0–G5 状态维持未通过，公开容器与源码检查继续不包含专有产物或真实存档。
